# ClusterMind — Engineering Notes

These instructions apply to AI coding agents and human contributors working in this repository.

## Architecture overview

```
src/
  lib/api.ts          Client-side data-access layer (demo vs. live mode)
  lib/impact.ts       Deterministic BFS blast-radius algorithm
  lib/types.ts        Shared TypeScript interfaces (ClusterSnapshot, ImpactResult, …)
  lib/workspace.tsx   React context for shared UI state
  data/demo-fixture.ts   Synthetic Kubernetes dataset (clearly labelled)
  routes/             TanStack Start file-based routes
  components/cm/      Application-specific components
  components/ui/      Radix/shadcn primitives

server/
  api/snapshot.get.ts    GET /api/snapshot — returns demoSnapshot
  api/impact.post.ts     POST /api/impact  — runs computeImpact
  api/investigate.post.ts POST /api/investigate — Gemini + demo fallback
  services/gemini.ts     Shared Gemini service (retry, prompt, validation)

vite-plugin-api-dev.ts  Dev-server middleware (mirrors production handlers)
vite.config.ts          Vite + TanStack Start + Nitro configuration
```

## Coding rules

- **All client data access goes through `src/lib/api.ts`.**  
  Components must not call `fetch()` directly. This keeps the Node/Gemini backend swappable without touching UI code.

- **Synthetic data lives only in `src/data/demo-fixture.ts`.**  
  Keep it clearly labelled. Never import it into production server code that would mix it with real cluster data.

- **Shared UI state lives in `src/lib/workspace.tsx`.**  
  Components remain free of hardcoded data.

- **Server-side secrets stay server-side.**  
  `GEMINI_API_KEY` and `GEMINI_MODEL` must never appear in client bundles, logs forwarded to Gemini, or Git-tracked files. Use `loadEnv()` in the Vite dev plugin; read `process.env` in Nitro handlers.

- **Gemini interprets evidence only.**  
  The prompt must supply only the timeline and blast-radius data from the demo fixture. Gemini must not invent graph edges or treat unverified hypotheses as confirmed facts. Evidence IDs are validated against the fixture after every response.

- **Business logic belongs in `server/services/`.**  
  HTTP handlers (`server/api/*.ts`) validate requests and return typed responses. They must not contain business logic; delegate to services.

- **Keep generated files where the framework expects them.**  
  `src/routeTree.gen.ts` is auto-generated by `@tanstack/router-plugin` — do not edit it manually.

- **Do not force broad dependency upgrades.**  
  Fix only what is broken. Pin versions deliberately.

## Environment variables

| Variable            | Scope             | Description                                          |
| ------------------- | ----------------- | ---------------------------------------------------- |
| `VITE_DEMO_MODE`    | Build-time client | `"false"` enables live API mode                      |
| `VITE_API_BASE_URL` | Build-time client | Override API origin (optional)                       |
| `GEMINI_API_KEY`    | Server runtime    | Gemini API key — never expose to the browser         |
| `GEMINI_MODEL`      | Server runtime    | Gemini model name (default: `gemini-3.5-flash-lite`) |
| `PORT`              | Server runtime    | TCP port (Cloud Run sets this automatically)         |

## Testing

- Unit tests: `src/lib/impact.test.ts` — deterministic BFS
- Integration tests: `src/test/server-api.test.ts` — all three API handlers
- App routing: `src/test/app-routing.test.tsx`

Run `npm test` before every commit. CI runs the same suite.

## Adding a new API endpoint

1. Create `server/api/<name>.<method>.ts` — validate request, delegate to a service.
2. Add the handler to `vite.config.ts` → `nitro.handlers`.
3. Add the route to `vite-plugin-api-dev.ts` → `configureServer` middleware.
4. Add a client function to `src/lib/api.ts` with a demo-mode branch.
5. Write tests in `src/test/server-api.test.ts`.
